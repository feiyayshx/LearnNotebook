# Spec Writing（需求规格说明书生成）

将三类输入（产品原型、需求雏形、已有代码）转化为无歧义、可验证、经用户确认的需求规格说明书。

## 优秀 Spec 的判定标准（内化目标）

源自 IEEE 830 / ISO 29148 / EARS / GitHub Spec-Kit 的调研结论，生成的每份 Spec 必须满足：

| 特征 | 含义 | 本流程的保障机制 |
|------|------|------------------|
| 无歧义 | 每个读者只有一种理解 | 模糊词扫描 + EARS 句式 |
| 完整 | 正常/异常/边界场景全覆盖 | 分维度缺口分析（clarification.md） |
| 可验证 | 每条需求可测试判定真伪 | 强制验收标准（Given/When/Then） |
| 一致 | 需求间不矛盾，与代码现状的冲突已裁决 | 冲突必问红线 |
| 单一 | 一条需求只说一件事 | 逐条编号撰写 |
| 必要 | 每条需求可追溯来源 | 来源标注 + 禁止脑补红线 |
| 可行 | 技术与资源可达成 | 代码现状勘查 |
| 已确认 | 无未核实的假设 | Open Questions 机制 |

关键认知：Spec 聚焦 **WHAT 和 WHY**，不写 HOW（技术选型、库、代码结构属于设计文档）；但已有代码的现状与约束作为**事实**记录在"现状与约束"章节。

## 五条红线（违反任意一条必须返工）

1. **未确认不写死**：未获用户明确确认的内容，不得作为确定性需求写入正文，只能进 Open Questions
2. **禁止脑补**：用户未提及的功能、角色、流程不得写入 In Scope；推测性需求必须标注【假设】并请求确认
3. **冲突必问**：输入源之间（原型 vs 口述 vs 代码）矛盾时必须提问由用户裁决，禁止自行选择
4. **假设必标**：所有假设标注【假设】并列入 Open Questions，确认后才移除标记
5. **事实与推测分离**：读过代码/文档的【已验证】事实，与未经核实的【推测】，必须分开陈述

## 工作流程（五阶段，顺序执行）

### 阶段 1：输入收集与现状勘查

三类输入源逐一收集，缺失的源需向用户确认"确实没有"：

**A. 产品原型**（图片 / 链接 / 设计文件）
- 图片路径：用 Read 读取，提取页面结构、字段、按钮、状态、跳转关系
- 链接：用 WebFetch 或浏览器工具打开分析
- 产出：原型要素清单（页面 / 字段 / 交互 / 状态流转）

**B. 需求雏形**（用户口述 / 聊天记录 / 文档草稿）
- 提取：目标用户、核心诉求、业务场景、成功标准
- 关键句保留原文引用，避免转述失真

**C. 已有代码**（需求涉及存量系统时必须勘查）
- 用 SearchCodebase 语义搜索相关模块、接口、数据模型、枚举
- 产出《现状事实清单》，每条标注【已验证】（读过代码）或【推测】（未核实）

阶段 1 产出《输入清单》并向用户确认完整性：

| # | 来源 | 类型 | 说明 | 状态 |
|---|------|------|------|------|
| 1 | ... | 原型/需求/代码 | ... | 已确认/待确认/缺失 |

- 原型或代码缺失：可继续，但必须在 Spec"输入来源"章节如实记录
- 需求雏形完全缺失：先访谈用户补齐核心意图，再进入阶段 2

### 阶段 2：需求澄清（核心阶段，决定质量上限）

1. **模糊点扫描**：用 [clarification.md](clarification.md) 的模糊词清单扫描全部输入与自己的初步理解
2. **缺口分析**：按 clarification.md 的分维度问题库逐项检查（角色、主流程、异常、边界、数据、权限、非功能、集成）
3. **结构化提问**：
   - 使用 AskUserQuestion，每轮不超过 4 个问题，优先问阻塞性最强的
   - 每个问题提供 2-4 个候选答案 + 推荐项（附理由），降低用户决策成本
   - 用户回答后复述确认："我的理解是…，对吗？"
4. **多轮澄清**直至：阻塞性问题清零，或用户明确指示"剩余问题标记即可"

禁止事项：
- 一轮抛出超过 4 个问题
- 把多个独立问题揉成一个问题
- 用"还有其他需求吗"这类空泛问题代替具体确认
- 未澄清完毕就直接动笔写 Spec

### 阶段 3：撰写 Spec

按 [template.md](template.md) 撰写，核心纪律：

- 需求用 **EARS 句式**：
  - 事件驱动：`当 {触发事件} 时，系统应当 {响应}`
  - 异常处理：`若 {异常条件}，则系统应当 {响应}`
  - 状态相关：`当处于 {状态} 时，系统应当 {响应}`
  - 可选特性：`若配置 {可选特性}，则系统应当 {响应}`
  - 恒常特性：`系统应当 {恒常属性}`
- 功能需求编号 FR-001…，非功能需求编号 NFR-001…，一条只说一件事
- 每条需求必须配验收标准（Given/When/Then 或可判定语句）
- 明确 In Scope / Out of Scope，Out of Scope 显式写"本期不做"，防范围蔓延
- 未确认项只进 Open Questions 章节；正文引用处标注【待确认 Q-x】

### 阶段 4：质量门禁自检

逐条核对，全部通过才能进入阶段 5。**此清单不是一次性关卡**——进入质量循环后（见下文），每次变更都必须重跑本清单；机械项优先用 `scripts/spec-lint.mjs` 自动执行：

- [ ] 全文模糊词扫描通过（清单见 clarification.md，脚本自动检查）
- [ ] 每条 FR/NFR 有编号、有验收标准、可测试判定（脚本检查编号唯一性与验收标准存在性）
- [ ] 正常 / 异常 / 边界场景全覆盖
- [ ] In Scope 与 Out of Scope 无交集、无矛盾
- [ ] 与代码现状的矛盾均已由用户裁决并记录
- [ ] 无未标注的假设；Open Questions 均写明影响与建议方案（脚本检查 Q-x 引用一致性）
- [ ] 需求之间无矛盾（同一场景交叉读两遍验证）
- [ ] 无实现方案污染（技术选型、库名、代码结构不出现在需求层）

### 阶段 5：用户确认与定稿

1. 向用户呈现：Spec 全文 + Open Questions 清单
2. 请用户逐项确认 Open Questions；每确认一项，更新正文并移除对应标记，**触发 H2 钩子完成重检后再确认下一项**
3. 迭代直至：满足质量循环退出条件（见下文）
4. **保存位置**：主动询问用户目标路径；用户无偏好时建议 `docs/specs/{YYYYMMDD}-{功能名}-spec.md`
5. 定稿后输出摘要：范围概述、需求条数、验收标准条数、遗留风险

## 质量循环（Quality Loop）与 Hooks

五阶段是主线，但 Spec 质量靠**每次变更后的重检闭环**保障：任何变更（用户回答澄清、Open Question 消解、用户手改文件、增删改需求条目）都触发重检，而非只在阶段 4 检查一次。

### 循环结构（有界）

```
变更发生
  → 1. 应用变更：更新正文 / 标记 / 元信息状态与确认进度
  → 2. 增量检查：本次变更引入的新问题（新模糊词、新矛盾、编号错乱、孤儿引用）
  → 3. 全量门禁：重跑阶段 4 检查清单（机械项运行 spec-lint.mjs）
  → 4. 漂移检测：变更与既有章节的交叉矛盾（重点：后确认的答案 vs 已写好的 FR/NFR）
  → 5. 发现问题 → 修复或转为 Open Question → 回到 1
```

**退出条件（全部满足）**：
- 阶段 4 门禁全过（spec-lint 退出码为 0）
- Open Questions 清零，或用户书面接受遗留项（写入"确认记录"）
- 最近一轮变更未产生任何新增问题

**有界约束**：同一会话内"自动修复 → 重检"循环不超过 3 轮；超限立即停止，输出未决问题清单交用户裁决，禁止无限自旋。

### Hooks（触发器 → 动作规则）

Skill 无系统级钩子，以下触发器规则必须严格遵守；机械项一律运行 `node scripts/spec-lint.mjs <spec文件路径>` 执行：

| # | 触发时机 | 动作 |
|---|----------|------|
| H1 | 用户回答澄清问题后 | 更新对应章节 → 对变更内容跑模糊词扫描 → 检查与既有需求的矛盾 |
| H2 | Open Question 被确认/关闭后 | 移除标记、更新正文 → 运行 spec-lint → 全量门禁重检 → 更新确认进度 |
| H3 | Spec 文件被 agent 以外方式修改（用户手改） | 重新读取全文 → 运行 spec-lint → 门禁重检 → 向用户报告变更差异与新问题 |
| H4 | 新增/修改/删除任意 FR/NFR 后 | 检查编号唯一性与连续性、验收标准存在性、Q-x 引用一致性（spec-lint 自动覆盖） |
| H5 | 每次回复用户前 | 输出质量快照：`门禁 x/8 通过 · Open Questions 剩 n · 未决冲突 n · 循环轮次 m/3` |

### 可执行钩子：scripts/spec-lint.mjs

每次变更后运行：`node scripts/spec-lint.mjs <spec文件路径>`，退出码非 0 即门禁不通过。自动检查项：

- 模糊词残留（词表与 clarification.md 第一节一致）
- FR/NFR 编号重复、验收标准缺失
- 【待确认 Q-x】引用与 Open Questions 表的一致性（孤儿引用报错、孤儿条目告警）
- 【假设】【推测】标记残留统计
- 模板占位符 `{}` 残留

矛盾检测、可测试性判断等语义项不在脚本能力内，仍由 agent 按阶段 4 清单人工执行。

## 流水线协作（可选上下游，存在时优先接驳）

```
env-bootstrap → spec-writing → spec-review → deliver-system → spec-loop-verify
└────────────────── ai-trace(横切度量,任务结束时聚合指标)──────────────────┘
```

- **第 0 环**：项目若经 env-bootstrap 初始化，优先使用其约定：spec 落盘 `docs/specs/`（替代默认建议路径）、未决项机制与 `docs/open-questions.md` 打通、项目简介与红线从 AGENTS.md 读取作为"现状与约束"输入；阶段 1 代码现状勘查优先读 `docs/maps/` 五张地图（代码/业务域/接口/数据/环境），再按需下钻源码，勘查中发现地图过时之处提请用户更新。
- **下游**：定稿后建议交 spec-review 独立评审（本 skill 的质量循环不替代独立评审）；定稿 spec 是 deliver-system 的 intent 权威源件与 spec-loop-verify 的交付标准——**NFR 必须写成可度量指标**（见模糊词改写表），否则验收阶段将被标为不可验证（BLOCKED）。
- **未决项交接**：Open Questions 未清零就流转下游时必须在文首标注；下游按各自规则降级处理（deliver-system → assumptions/questions；spec-loop-verify → 对应检查点预判 BLOCKED）。
