# Spec 评审维度清单

> 6 大维度是思考框架，不是凑数清单：某维度无问题就跳过，禁止为覆盖维度而硬找问题。

## 1. 一致性（Consistency）

同一事物在不同位置的表述必须一致。

- **版本演进残留**：需求方向变更后，旧方案是否仍残留在接口清单、数据模型、伪码/流程、页面/组件清单、验收用例、附录中。全文检索旧方案关键词，命中处应只剩「废止声明」
- **术语统一**：同一概念的命名一致（实体名、状态名、操作名、按钮文案）
- **枚举口径**：状态/类型枚举在表字段注释、字典定义、页面文案、验收用例中的取值与含义一致（常见坑：字段注释 3 态、字典 6 态）
- **文档 ↔ 原型**：页面结构、字段、操作入口、文案一致；冲突处需声明以谁为准
- **引用完整**：被引用的规则编号/章节存在且语义匹配，无悬空引用（如引用了 BR-04a 但规则表无此编号）

## 2. 完整性（Completeness）

- **数据模型**：规则声称要存的数据，表结构里都有对应字段；1-N 多值关系有明细/关联表；多次同类记录（如多条凭证）有流水表而非单字段；审计字段满足多次操作的留痕需求（避免单组审计字段互相覆盖）
- **接口契约**：每个用户动作有对应接口；入参足以支撑业务校验与页面回填；返回结构覆盖页面展示所需全部字段
- **状态机**：覆盖全生命周期（含终态定义）；每个状态有进入条件与出口动作；异常路径（驳回/取消/超时/关闭）有定义；终态后的操作有拦截
- **角色 × 权限**：每类角色的数据可见范围与操作边界明确；越权访问有拒绝策略
- **异常与边界**：参数非法、并发冲突、重复提交、数据量过大、依赖失败的期望行为有定义

## 3. 正确性（Correctness）

- **计算/公式**：边界条件（0、负数、小数精度、闰年/时区、跨周期）；不同类型/模式分支是否需区别对待（常见坑：统一公式未区分类型导致多算/少算）；单位与量级
- **逻辑推演**：规则 A 与规则 B 组合是否产生矛盾结果；流程伪码与规则正文描述一致
- **数值口径**：同一数值（窗口期、上限、比例、默认值）全文唯一出处且处处一致（常见坑：正文 90 天、验收用例 30 天）

## 4. 明确性（Clarity / 可开发性）

- **无悬而未决**：不出现「实现时确定/二选一/待填」且未指明决策人；待确认项有建议默认与关闭时限
- **行为可判定**：任何输入下开发能确定程序行为（如：超额是拒绝还是截断；冲突是覆盖还是报错）
- **定义精确**：编号/编码规则给出格式 + 示例 + 并发唯一策略；接收人/范围给出可判定集合（角色编码/权限标识），而非「相关人员」
- **文案确定**：提示语、按钮名、状态文案给出具体措辞或唯一来源，不含混

## 5. 可验证性（Acceptance）

- **AC ↔ 规则映射**：每条业务规则至少一条验收用例；AC 有可断言的预期结果
- **三类场景覆盖**：正常流、异常流、边界值均有 AC
- **端到端可跑**：主流程有 E2E 场景与通过标准
- **非目标声明**：明确本期不做什么，防止范围蔓延与误验收

## 6. 工程约束（Engineering Constraints）

- **存量关系**：与既有功能/数据/接口的关系（复用/旁路/替换）有说明；不破坏既有行为；引用的现网能力真实存在（不得依赖不存在的接口/服务/枚举值，新占用的编号/码段需与现存不冲突）
- **依赖与边界**：跨模块/跨服务调用方式符合项目架构约束
- **性能/安全/合规**：指标明确且可达（重接口如导出/批量不应套用普通响应指标）；敏感数据处理（脱敏、权限、留存）有要求
- **数据与配置变更**：增量、幂等、可回滚；有回滚方案
- **可实施性**：方案所需的资源/账号/第三方能力有明确获取方式与责任方
