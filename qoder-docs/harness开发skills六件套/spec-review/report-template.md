# 评审报告模板

> 使用说明：按本模板生成 `{spec文件名}-评审意见.md`。
> 原则：结论先行；每条问题四要素（位置/问题/原因与影响/修改建议）；无对应级别问题时写「无」，不凑数；全文避免冗余复述。

---

```markdown
# {文档名称} 评审修改意见

| 项目 | 说明 |
|------|------|
| 评审对象 | {spec 文件路径及版本} |
| 输入材料 | spec ✓ / 原型 {✓ 或 ✗} / 约束文档 {✓ 或 ✗} |
| 评审日期 | {YYYY-MM-DD} |
| 总体结论 | {一句话：是否具备开发条件 + 主要问题概览} |

问题分级：**P0**=阻断开发（必错/返工）；**P1**=必扯皮（未定义/口径冲突）；**P2**=质量优化。
统计：P0 ×{n} · P1 ×{n} · P2 ×{n}
```

## 模板字段说明

| 区块 | 作用 | 写作要求 |
|------|------|----------|
| 总体结论 | 让读者 10 秒判断能否开发 | 一句话，含 P0 数量与最致命问题 |
| 问题条目 | 可执行修复的依据 | 修改建议必须具体到「改什么、改成什么样」，禁止「建议优化一下」式空话 |
| 待决策清单 | 区分「文档缺陷」与「业务未定」 | 仅放文档作者无法拍板的事项；每条给建议默认 |
| 写得好的部分 | 防止修复误伤、避免纯负面报告 | 简短列举，不溢美 |
| 修复建议路线 | 大改时分步，降低交叉修改风险 | 仅问题 ≥5 条或需大规模重排时填写 |
