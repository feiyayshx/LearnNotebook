# Spec Loop Verify（有限循环验证）

## Overview

以**用户确认的交付标准**为唯一事实来源（Ground Truth），把验收点变成可执行检查点，用真实操作（接口调用、UI 自动化、SQL 断言）取证比对；不符则在授权范围内修复并重验。循环由**检查计划文档**唯一驱动，全程落文档，防止漂移。

本 skill 是**项目无关**的：所有环境信息（技术栈、配置来源、中间件、账号凭据、项目红线）一律在 Phase 0/Phase 2 通过**向用户询问 + 从仓库探测核对 + 方案选择**获得，禁止假设或沿用其他项目的取值。

**核心原则：证据先于结论，计划驱动循环，每步落文档，修复不越界。**

## The Iron Law（六条铁律）

```
1. CONFIRM BASELINE FIRST   —— 未与用户对齐交付标准（文档集+范围+环境+授权），禁止开始任何验证
2. NO PASS WITHOUT EVIDENCE —— 没有当轮新鲜证据（SQL 输出/接口响应/截图/网络日志），禁止判定 PASS
3. NO UI PASS WITHOUT RENDER—— 含 UI 的检查点，页面未在真实运行环境（浏览器/小程序/模拟器/真机等）渲染
                               并完成交互断言，禁止判 PASS；工具降级只能降结论（→BLOCKED/人工必验），不能降标准
4. PLAN IS THE LOOP         —— 循环只执行 plan.md 中的检查点；变更计划必须先记 ADR 并经用户确认
5. BOUNDED LOOP             —— 最多 MAX_ROUNDS 轮（默认 3）；同一检查点失败 3 次禁止第 4 次修复
6. SCOPED FIX ONLY          —— 只改授权范围内文件；不脑补需求；不顺便优化；遵守项目红线
```

## 阶段总览

```
Phase 0 交付标准对齐 + 环境画像（用户确认，记 ADR-001）
   → Phase 1 生成检查计划 plan.md（用户确认）
   → Phase 2 环境预检（GATE，不过则停）
   → Phase 3 有限验证循环（每步更新 plan/report/fixes/adr）
   → Phase 4 收尾（报告定稿 + 清理 + 待决项）
```

## Phase 0：交付标准对齐（Baseline Alignment）

**禁止跳过。** 用 AskUserQuestion 与用户逐项确认（可在一条消息中多问）；能从仓库探测到的项先探测、再向用户**核对**而非开放式提问：

| 对齐项 | 说明 | 示例 |
|--------|------|------|
| 交付标准文档集 | 1~N 份：开发 Spec / 交付标准或验收文档 / 设计原型（HTML/图片/Figma 导出）/ 接口文档；明确**优先级与冲突裁决顺序** | spec.md + prototype.html，冲突时原型优先 |
| 模块与范围 | 验证对象（模块/功能域）；**授权修复的文件白名单**；明确排除项（Non-Goal） | 订单模块 + 前后端对应目录；不含支付主流程 |
| 递归依赖 | 从标准文档展开的依赖模块（消息/权限/菜单/任务调度等），默认只验证不修复 | 消息服务、菜单权限表、定时任务 |
| 技术栈与环境画像 | 后端/前端技术栈与构建启动命令、配置来源（配置中心/本地配置/环境变量）、接口形态与统一响应结构（REST/GraphQL/gRPC/CLI/消息）；先从仓库探测（构建文件、lock 文件、配置文件），再向用户核对 | Maven 多模块 + 配置中心；REST，响应统一 code/data 包裹 |
| 交付形态 | 本次交付包含哪些形态（可多选）：Web 管理端 / H5 / 小程序 / 原生 App / 桌面端 / 纯后端 API / CLI 工具 / SDK·库 / 数据管道·批处理；**每种形态决定 E2E 手段与预检章节**（映射见 env-preflight §0 与 verification-techniques §层 C） | 纯后端 API + 管理端 |
| 环境与 PROFILE | 目标环境（本地 dev / 测试环境）、数据造数授权（共享库必须明示同意） | dev，本地启动服务，允许造数 |
| 循环与修复授权 | MAX_ROUNDS（默认 3）；修复模式：受限自动修复 / 只报告 / 先报告后确认修复 | 3 轮，受限自动修复 |
| 项目红线 | 禁止触碰的模块/主流程、依赖方向约束、禁用的框架或组件、数据库变更约束等；用户明示"无"也要记录 | 不碰结算主流程；SQL 只增不删改；旧接口只追加字段 |
| 账号与凭据 | 各端测试账号、角色对照账号；缺失项登记 | 平台管理员、无权限账号、各业务角色测试号 |

产出：确认结果写入 `RUN_DIR/adr.md` 首条 **ADR-001（基线确认）**，并初始化 `RUN_DIR/plan.md` 头部（依据文档清单+版本+范围）。任何一项用户表示"不确定"→ 登记为待决 ADR，对应检查点预判 BLOCKED。

## Phase 1：生成检查计划（plan.md）

**Step 1 基线一致性预检（先矛盾扫描，后提取）**：通读交付标准文档，先集中扫描**内部矛盾**（版本残留、数值/规则前后不一致）与**文档间冲突**（spec vs 原型 vs 接口文档），产出 SPEC-ISSUE 清单交用户裁决并落 ADR，再提取检查点；禁止带着未决矛盾写计划。HTML 原型必须连 script 一起读（状态机/计算公式/文案映射常以 script 为准），只读模板视为跳读。

**Step 2 逐字精读提取**：按 [references/run-documents.md](references/run-documents.md) §plan.md 模板生成检查计划：

- **检查点全覆盖**：标准文档中全部 AC/验收条目、业务规则、端到端场景、UI/交互要求、非目标回归项；每条给出 层级（FUNC/INTEG/E2E/NFR）、端、前置条件、操作步骤、预期-接口/DB/UI、出处章节。
- **四类隐性检查点（AC 之外必须补入，历史漏检重灾区）**：
  1. **交互可达性**：每个业务动作都必须存在从 UI 入口到完成的完整点击路径（入口存在→可点→中间态可过→可提交→可返回）；禁止用直调接口手传参数替代 UI 交互链（会掩盖「入口缺失/弹窗打不开/确认态不联动」类缺陷）。
  2. **前端消费层**：接口通过 ≠ 页面能用；每个列表/详情/导出类 CP 必须断言「前端真实渲染出了数据/产物文件打开有内容」（三大断层高发区见 verification-techniques.md §前端消费层）。
  3. **业务闭环 sanity**：状态机每个状态都有出路（不存在「到期了但不能续费」类死胡同）；每条数据对每个相关角色都有可见路径；时间边界（当天、起止相同、创建即临界）不产生荒谬展示；命中时记 SPEC-ISSUE 交用户裁决（spec 符合 ≠ 业务可用）。
  4. **UI 一致性与文案规范**：同类组件同一风格、无文本截断/横向滚动/字号不统一、无「选填/预留/后续」等非正式文案（清单见 verification-techniques.md §UI 一致性走查）。
- **边界矩阵**：每个涉及金额/集合/文本/时间的 CP 至少覆盖：多条记录累加（≥2 笔，防字符串拼接/快照读）、空数据渲染、超长文本、临界日期（当天/相同起止/创建即满足条件）、重复提交/并发。
- **NFR 检查点（非功能验收）**：交付标准中**明示且可度量**的性能/容量/安全/容错指标（如 P95 ≤ 500ms、单表百万行分页可用）逐条建 CP（层级 NFR，断言配方见 verification-techniques §层 D）；指标不可度量 → 记 SPEC-ISSUE 交用户裁决；缺测量手段 → 该 CP 预标 BLOCKED 并在 GATE 时告知用户，禁止静默跳过或用主观感受替代数据。
- **递归依赖点**：依赖模块的集成检查点（D- 前缀）。
- **凭据需求矩阵**：列出每个 CP 执行所需的账号/凭据/角色（有权限管理员、无权限对照、各状态测试用户、配置中心/调度平台/小程序登录态等），供 Phase 2 一次性核销。
- **数据依赖链**：标注 CP 间状态依赖（如"状态 X 的单据"是多个 CP 的共同前置），规划共享造数（造一次复用），并据此排列执行顺序。
- **冲突裁决**：按 Step 1 产物取值；无法取值的 → 该点 BLOCKED 并问用户。
- **GATE**：计划生成后向用户汇报检查点总数、分层分布、凭据矩阵、依赖链，经确认才进入 Phase 2。

## Phase 2：环境预检（Preflight Gate）

按 [references/env-preflight.md](references/env-preflight.md) 执行（通用手册：先按 Phase 0 环境画像与交付形态做**方案选择**，再按**形态适用矩阵**逐项预检，不适用章节记 N/A）：配置来源解析 → 数据断言通道 → 业务服务 → 网关/代理通路 → 各端运行与自动化能力 → 凭据核销与造数。所有连接信息**从活配置取、缺失向用户问**，禁止沿用任何历史项目取值。

**GATE：任一硬项不通过 → 停止，输出缺口清单请用户处理。**

## Phase 3：有限验证循环（核心 Loop）

```
FOR round = 1 .. MAX_ROUNDS:
  1. RE-READ   重读 plan.md（禁止凭记忆执行，防漂移）
  2. EXECUTE   按 plan 依赖序逐检查点执行（先备好共享造数，FUNC → INTEG → E2E）：
               操作 → 断言接口 → 断言 DB → 断言 UI → 判定 PASS/FAIL/BLOCKED
  3. LOG       每完成一个检查点：证据落盘 evidence/<CP-ID>/，
               立即更新 plan.md 状态列（见 run-documents.md §更新时机矩阵）
  4. IF 无 FAIL 且无 BLOCKED → 跳出，进 Phase 4
  5. IF round == MAX_ROUNDS  → 跳出，残余项进 Phase 4 上报
  6. FIX       按修复协议处理 FAIL 点；每个修复动作后立即登记 fixes.md；
               轮末更新 report.md + adr.md（轮次小结）→ 向用户简报 → 下一轮
```

**防漂移规则（违反 = 本轮无效）：**

- 检查点的**增删改**只能走 ADR 变更流程（用户确认）后改 plan.md，禁止在循环中顺手加测/跳测；
- **预期值只能来自交付标准**；修代码可以，改预期值必须 ADR + 用户确认；
- 证据必须当轮新取，禁止复用上一轮截图/查询结果充当重验证据；
- 修复只针对 FAIL 点，单个修复一个根因；失败计数累记在 plan.md `fail_count` 列。

**E2E 完成门槛（结束 loop 的硬条件）：**

- E2E 的手段随**交付形态**（Phase 0 确认）而定，但"全部通过才能结束 loop"的门槛对所有形态一致（工具矩阵见 verification-techniques §层 C）：
  - **含 UI 形态**（Web 管理端/H5 用 **chrome-devtools MCP / playwright MCP / browser-use**；小程序用 **miniprogram-automator/微信开发者工具自动化**；原生 App 用 **Appium/Maestro 类真机·模拟器自动化**；桌面端用 OS 级 UI 自动化）：对**全部功能逐步骤真实走查**（打开页面→点击→填写→提交→断言渲染与控制台/日志无错）；
  - **无 UI 形态**（纯后端 API/CLI/SDK·库/数据管道）：E2E = 从**真实入口**执行完整业务场景链——API 按业务旅程编排真实调用序列、CLI 以真实进程调用（含退出码/输出/产物文件断言）、SDK·库以独立示例工程按文档消费、数据管道以真实触发跑全链路——逐步断言中间状态与最终产物；
- 仅两种例外允许带未完成项结束：① 必须由用户提供信息/凭据才能继续（记 BLOCKED+缺口清单）；② 同一障碍累计 3 次无法解决（记 ESCALATED+根因分析）；除此之外禁止以「UI 细节转人工抽验」为由关闭 loop；
- **工具降级阶梯**（任一 UI 端自动化受阻时按序穷尽，每降一级记 ADR）：元素级断言 → 页面状态/路由断言+截图 → 同源替代环境（如小程序的 H5 编译产物用浏览器工具走同源页面）→ 仍不可行才标 BLOCKED 交用户人工；降级后该 CP 的结论上限是 BLOCKED（铁律 3），不得标 PASS 后附「人工抽验」了事；
- **过程件留存**：走查产生的逐步截图/页面快照/控制台日志，统一暂存到 `<workspace>/loop-test-<yyyymmdd-HHmmss>/<端>/<CP-ID>/`（项目根目录，按端与检查点归档）；判定用的关键证据同步归档 `RUN_DIR/evidence/<CP-ID>/`；loop 结束后 loop-test 目录经用户确认后可清理；
- **修复后重验必须升层**：无论缺陷在哪层发现，只要修复触碰了前端文件或接口出参，重验必须做到 UI 渲染层（防修复引入 UI 回归，如组件 API 误用、类名冲突）。

**受限自动修复协议：**

1. 先定位根因（读报错/日志/最小复现，systematic-debugging），禁止瞎改试探；
2. **同类排查**：根因确定后，用 Grep 在白名单范围内扫描同模式缺陷（如集合只取首个元素展示、缺防重拦截、硬编码枚举文案、表单无防重提交），命中点汇总记一条 ADR 决策"整类修复/逐点修复"；白名单外的命中只写入报告，由用户决定是否扩范围；
3. **风格一致**：动手前先找同类既有实现作参照（后端参考同模块 Service/Controller，管理端参考既有页面的组件与交互模式，小程序参考既有页面与样式约定），禁止引入新组件库/新样式风格/新依赖；fixes.md 记录参照实现；
4. 仅改授权白名单文件；涉及递归依赖模块 → 只出建议，用户确认后才动；
5. 遵守项目红线（Phase 0 确认并记入 ADR-001 的清单；常见形态：禁止触碰某核心主流程、模块依赖方向约束、禁用某框架/组件、旧代码只追加、新字段带默认值、SQL 只增不删改）；
6. 改后端须按项目构建命令重新构建并重启对应服务（改过被依赖的公共/API 模块先构建安装该模块），改前端待热更新生效后再重验；
7. **UI 微调授权（默认包含在受限自动修复内）**：在**不改设计、不改内容、不引入新风格**的前提下，可直接修复 UI 一致性类问题：文本截断、横向滚动、字号/对齐/间距不统一、非正式文案替换、缺失返回入口；涉及布局结构/交互模式/配色体系变更的美化则只列建议交用户决策；
8. 先单点重验转 PASS（重验层级见上方「升层」规则），再下一轮全量回归；
9. **同一 CP 累计失败 3 次 → 标记 ESCALATED 停修**，连同根因分析上报用户。

**分层要点（操作配方见 [references/verification-techniques.md](references/verification-techniques.md)）：**

| 层 | 范围 | 手段 |
|----|------|------|
| FUNC | 单入口+单数据单元：CRUD、校验、计算、状态机 | 接口/入口直调（REST/GraphQL/gRPC/CLI/函数级）+ 数据层断言（SQL 或替代通道，见 env-preflight §2） |
| INTEG | 跨模块链路：网关/RPC/MQ/消息/任务/权限 | 链路调用 + 跨库断言 + 触发任务 |
| E2E | 真实用户旅程/完整业务场景链 | 按交付形态选择手段（形态→工具矩阵见 verification-techniques §层 C）+ 全栈断言 |
| NFR | 非功能指标：性能/容量/安全冒烟/容错降级 | 轻量压测/量级造数/授权内故障注入 + 指标断言（见 §层 D）；超纲显式 BLOCKED |

## Phase 4：收尾（Closeout）

1. `report.md` 定稿：追溯矩阵（验收条目 → CP → 结果 → 证据）、不符项与修复、SPEC-ISSUE、残余风险、非目标回归证明（如 `git diff --stat` 范围证据）；
2. 造数清理执行并记录状态；**清理后必须告知用户副作用**（被删测试账号的缓存登录态需重新登录、有缓存的主数据需走页面修改等）；
3. 全部待决 ADR 汇总给用户（BLOCKED/ESCALATED/假设项）；
4. **结束条件自检**：含 UI 的 CP 全部经真实渲染走查（铁律 3 / E2E 完成门槛）；未达成的只能是 BLOCKED/ESCALATED 两类并附缺口清单；
5. **结论措辞规则**：只有全部 CP 为 PASS 才能说"验证通过"；否则只能陈述"X/Y 通过，残余 N 项"，禁止"基本通过/应该没问题"。
6. **地图失真上报**：验证中发现 `docs/maps/` 地图或项目文档与实际不符（接口前缀/表结构/状态机/环境入口等），逐条列入 report.md 残余风险并附证据；地图在授权白名单内可直接修正，否则建议回流 env-bootstrap 增量体检；禁止静默忽略。

## Red Flags —— 出现即停，回到流程

- 未对齐交付标准就开始提取检查点 / 开始验证
- **沿用历史项目的环境取值（地址/账号/表名/红线），而不是询问用户或从当前仓库探测**
- 未做基线矛盾扫描就生成计划；只读原型模板不读 script
- 凭据未核销就进循环，中途大面积 BLOCKED 返工
- 凭记忆执行检查点，不重读 plan.md；执行后不回写状态
- 循环中顺手新增检查点、跳过"明显没问题"的检查点
- 为提高通过率放宽预期值，而不是报告偏差或走 ADR
- 用上一轮证据充当本轮重验证据；UI 只截图不断言
- **用 API 直调手传参数替代 UI 交互链，跳过入口/弹窗/确认态的真实可达性**
- **UI 工具降级后仍判 PASS+附「人工抽验」关闭 loop，而不是标 BLOCKED 穷尽降级阶梯**
- **列表/导出类 CP 只断言接口响应/请求参数，不断言页面渲染出数据/产物文件内容**
- **修复触碰前端文件后只在发现层（API/DB）重验，不升到 UI 渲染层**
- **发现业务死胡同（状态无出路/数据不可达/时间边界荒谬）却因「符合 spec」不记 SPEC-ISSUE**
- 修复不找同类参照，引入项目没有的新风格/新依赖
- 修完一处不做同类排查，同模式缺陷留在白名单其他文件里
- 修复范围超出白名单；第 4 轮还想"再试一次"
- 发现标准文档矛盾后自行选择其一，不记 SPEC-ISSUE/ADR
- 凭配置文件"看起来有路由"就判通路 OK，不发真实请求
- 同一前置状态反复造数，不规划依赖链
- 造数后不清理；测试数据无 `[VERIFY]` 类前缀隔离；清理后不告知用户登录态/缓存影响（如已删测试账号的旧 token 会报用户异常）

## 流水线协作（可选上下游，存在时优先接驳）

```
env-bootstrap → spec-writing → spec-review → deliver-system → spec-loop-verify
└────────────────── ai-trace(横切度量,任务结束时聚合指标)──────────────────┘
```

- **上游**：项目若经 env-bootstrap（第 0 环）初始化，其产物（AGENTS.md、`.qoder/rules/` 红线、`docs/maps/` 五张地图、`service-map.yaml`、`docs/env/env-report.md`）可直接作为 Phase 0 环境画像与项目红线的探测线索（活配置仍为准，分工：env-bootstrap 管协作资产就绪与静态登记，本 skill 管运行时预检）。优先采用 spec-writing 定稿、spec-review 评审通过的 spec 作为交付标准；其 Open Questions 未清零 → 对应检查点预判 BLOCKED，并建议用户先回流澄清。deliver-system 交付的模块，其 `delivery-docs/`（acceptance、feature-ledger、verification 证据）可作为范围与凭据矩阵的参考输入，但**判定所用证据必须本 skill 当轮新取**（铁律 2）。
- **diff 门禁联动**：项目存在 `scripts/diff-gate.mjs`（env-bootstrap D1-6）时，进入修复循环前把授权修复白名单同步写入 `.qoder/diff-scope.txt`，loop 结束后清空。
- **ai-trace 联动**：项目启用 AI 提交归因时，本 skill 产生的修复提交带 `--author="qoder <qoder@ai.local>"`；loop 结束建议执行 `/ai-trace close` 聚合本次验证指标（RUN_DIR 是其首要挖掘源）。
- **下游回流**：验证产出的 SPEC-ISSUE 清单建议交 spec-review/spec-writing 修订文档后再继续或复验；report.md 追溯矩阵可直接作为送测/交付材料；影响长期架构的运行内 ADR 决策，收尾时建议升格一条到 `docs/decisions/adr/`（全链路唯一 ADR 落点）。
